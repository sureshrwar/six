0.  HEADLINE
--------------------------------------------------------------------------------

SIX boots on a gLinux cloudtop, mounts a root filesystem that was built from
source minutes earlier, loads a guest ELF binary, delivers a real SIGALRM to
it, and drops you at an interactive shell that can fork, exec and wait:

    VFS: Mounted root (ext2 filesystem).

    Ok i just have had enough of x86. so far i have been porting
    this stuff back and forth across intel and x86 - but dont
    have any more patience or energy.
    ...
    i-am-dumb> ls
    bin  dev  etc  lost+found  tmp
    i-am-dumb> date
    Wed Aug 19 07:51:15 GMT 2026
    i-am-dumb> pwd
    /
    i-am-dumb> fortune
    Some things better stay closed.
      - fortune
    i-am-dumb> exit

That paragraph of text is the author's own note, recovered from the 2005 disk
image before it was deleted, explaining why he abandoned the x86 port.  It is
now being read off a freshly built ext2 filesystem by a program the build
produced, running under a Linux 2.0.11 kernel that is itself an ordinary
32-bit Linux process.

The last time this worked was on Solaris, twenty-one years ago.


--------------------------------------------------------------------------------
1.  WHAT CHANGED SINCE REPORT v3
--------------------------------------------------------------------------------

Report v3 ended with the guest loaded and running but stuck: it had issued
alarm(1), installed a SIGALRM handler and called sigsuspend(), and then hung
forever.  Six bugs stood between that and a usable shell.  Five were in the
1000-2005 code; one was mine.


1.1  setup_frame() was still SPARC-shaped
     arch/six/kernel/signal.c

     The function that builds a signal frame on the guest's stack passed the
     handler address and the sigcontext pointer in %g6 and %g7.  x86 has no
     global registers; the pt_regs fields of those names are plain memory the
     guest cannot read.  It reserved 96 bytes below the frame -- a SPARC
     register window -- and, decisively, it wrote the new stack pointer into
     regs->esp.

     struct pt_regs is an overlay on glibc's ucontext_t, which carries two
     stack pointer slots:

         gregs[REG_ESP]   word 12   SIX calls it "kesp"
         gregs[REG_UESP]  word 22   SIX calls it "esp"

     The Linux kernel fills both identically when it delivers a signal, so
     reading either works.  But glibc's setcontext() -- which is how SIX
     returns to a guest (RESTORE_USER_CONTEXT) -- reloads %esp from REG_ESP
     and ignores REG_UESP entirely.  So every signal frame the 2005 code built
     was constructed correctly and then silently thrown away.

     This is the same trap that makecontext() sidesteps by writing kesp, which
     is why process creation worked and signal delivery did not.

     Fixed: the x86 path hand-builds an ordinary cdecl call frame below the
     sigcontext -- return address, sigcontext pointer, handler pointer --
     aligned the way the i386 ABI guarantees at a function entry point
     (%esp+4 a multiple of 16), and writes both stack pointer fields.


1.2  The guest trampoline read its arguments out of %mm4
     library/sys/sigreturn.c

     The x86 branch did:

         __asm__("movq %%mm4, (%1)" : "=r"(ret) : "r"(valp));

     This is the MMX channel.  Linux zeroes FPU state before entering a signal
     handler, so %mm4 always read back as zero and the trampoline called
     address 0.  (gdb caught it exactly: eip 0x00000000, return address
     0x0300151c, which is the instruction after "call *%eax" inside
     sigreturn.)  This is the third time the MMX channel has been proven dead
     in this project.

     Fixed: sigreturn() is now

         int sigreturn(struct sigcontext *sc, int (*handler)());

     and takes its arguments from the frame setup_frame() built.


1.3  sys_sigreturn() restored a dangling fpregs pointer
     arch/six/kernel/signal.c

     glibc's ucontext_t is self-referential: uc_mcontext.fpregs points at the
     __fpregs_mem array inside the same structure.  Copying a context
     elsewhere and copying it back leaves that pointer aimed at the copy.
     six_fix_context() repoints it; sys_sigreturn() now calls it.


1.4  /dev/tty1 was created as character major 0, minor 0
     port/image/manifest.txt

     Nothing is registered at character major 0.  sys_open() therefore failed
     with ENODEV in init(), and because stock Linux 2.0 ignores that return
     value, /bin/sh was started with no file descriptors at all.

     Every write(1, ...) the shell made returned -EBADF.  The shell had in
     fact been working for some time; it simply had nowhere to write.  It
     opened /etc/x86.txt (which became fd 0, the lowest free descriptor --
     itself the clue), read it correctly, wrote it into the void, printed a
     prompt into the void, and exited.

     The 2005 image had 4:1 for /dev/tty1 and 4:0 for /dev/console -- verified
     with debugfs against git tag v2005-cvs before that image was deleted.
     The manifest now says so.  init() reports the failure rather than
     ignoring it, so this cannot happen quietly again.


1.5  A non-blocking read() returning -1 was treated as a keystroke
     include/asm-six/io.h

     This is the best bug of the session.  inb_p(0x64), the emulated keyboard
     status port, did:

         kcount = read(TERMFD, kchar, 512);
         if (kcount == 0) return 0;     /* no key waiting */
         else             return 0x01;  /* key waiting    */

     TERMFD is the host's /dev/tty, opened raw and O_NDELAY.  Non-blocking
     means read() returns -1/EAGAIN whenever nobody is typing -- which is
     essentially always, since the timer interrupt polls this port ten times
     a second.

     -1 is not 0.  So the status port reported a keystroke waiting, and
     inb_p(0x60) then did "if (kcount) { kcount--; return kchar[koff++]; }",
     driving kcount through -1, -2, -3... and koff forward: replaying the last
     line the user typed, over and over, and then reading off the end of a
     512-byte static buffer into whatever the linker happened to put next.

     handle_scancode() in drivers/char/keyboard.c treats the letter 'q' as
     "reset the tty and exit(0)" -- the author's emergency escape hatch.  So a
     few seconds after the first keypress, SIX reliably fed itself a 'q' out
     of stale memory and shot itself, with no message and exit status 0, while
     the guest sat innocently blocked in read().  It looked exactly like the
     shell deciding to quit.

     Fixed: test "<= 0" in both places and clamp kcount.


1.6  libc.a did not depend on the objects it absorbs
     library/libc/Makefile, Rules.guest          [my bug, introduced in M6]

     library/libc/lib/libc.a is built by "ar -r libc.a $(OBJS) $(SYSOBJS)"
     where SYSOBJS was $(wildcard ../sys/*.o).  A wildcard over object files
     is not a dependency.  Editing a system call stub rebuilt ../sys/foo.o and
     ../sys/lib/libsys.a and left libc.a -- the archive guest programs are
     actually linked against -- untouched.

     The consequence was that the fix in 1.2 was in the tree and not in the
     binary, and I spent a while disassembling a shell that still contained
     "movq %mm4" after I had deleted that line.

     Fixed: SYSOBJS is derived from ../sys/*.c and named as a real
     prerequisite.  Separately, Rules.guest grew -MMD header dependency
     tracking, so the guest build is no longer the only part of the tree
     without it.


1.7  SIX_TRACE_GUEST_SYSCALLS did not trigger a rebuild
     Makefile, arch/six/kernel/Makefile

     Changing a -D on the make command line is invisible to make: irq.o is
     newer than irq.c either way.  "make SIX_TRACE_GUEST_SYSCALLS=0" after a
     traced build appeared to succeed and produced a binary that still traced.
     The value is now recorded in arch/six/kernel/.trace_flag, rewritten only
     when it changes, and irq.o depends on it.


1.8  rebuild.sh now really does a full build
     port/tools/rebuild.sh

     It used to skip library/ and applications/ deliberately, from the days
     when they did not compile.  They compile now, and the disk image is
     generated from them, so a "full rebuild" that skipped them could ship an
     image full of stale binaries.  It cleans and rebuilds everything, with
     SIX_USERLAND=y.

2.  WHAT NOW WORKS, END TO END
--------------------------------------------------------------------------------

Observed in a single run, with SIX_TRACE_GUEST_SYSCALLS=1:

    guest[1] syscall 27   alarm(0)                  sleep(1) begins
    guest[1] syscall 67   sigaction(SIGALRM, ...)
    guest[1] syscall 67   sigaction trampoline addr (two-trap protocol)
    guest[1] syscall 27   alarm(1)
    guest[1] syscall 72   sigsuspend(&ss)
    ...                   one second of emulated time passes
    guest[1] syscall 119  sigreturn(sc)             <-- SIGNAL DELIVERED
    guest[1] syscall 27   alarm(0)
    guest[1] syscall 67   sigaction restore
    guest[1] syscall 5    open("/etc/x86.txt")
    guest[1] syscall 3/4  read/write x 4            <-- the file appears
    guest[1] syscall 6    close
    guest[1] syscall 4    write(1, "i-am-dumb> ", 11)
    guest[1] syscall 3    read(0, buf, 1024)        <-- keyboard works
    guest[1] syscall 2    fork()                    <-- child is guest[4]
    guest[1] syscall 7    waitpid(4)
    guest[4] syscall 11   execve("/bin/hello", ...)
    guest[4] syscall 1    exit(0)
    guest[1] syscall 4    write(1, "i-am-dumb> ", 11)

and for a more interesting child, guest[7] running /bin/ls:

    guest[7] syscall 45   brk x3
    guest[7] syscall 106  stat("/")
    guest[7] syscall 33   access("/")
    guest[7] syscall 5    open("/")
    guest[7] syscall 141  getdents x2
    guest[7] syscall 6    close
    guest[7] syscall 54   ioctl(1, TIOCGWINSZ)
    guest[7] syscall 4    write(1, "bin  dev  etc  lost+found  tmp\n", 31)

So: process creation, program loading, the filesystem, the block device, the
console in both directions, the timer, and signal delivery are all functional.

3.  HOW TO BUILD AND RUN IT
--------------------------------------------------------------------------------

    cd /usr/local/google/home/motorman/work/six/v1/six
    port/tools/rebuild.sh            # full clean build, kernel + userland + image
    ./six                            # hit ENTER at the prompt

Type "exit" to leave the shell.  Typing "q" anywhere quits SIX itself -- that
is deliberate, and dates from 2003; see handle_scancode() in
drivers/char/keyboard.c.

To watch every system call a guest makes:

    make SIX_TRACE_GUEST_SYSCALLS=1
    ./six

For scripted runs, note two things learned the hard way:

  * "timeout 25 ./six" does not work.  SIX catches nearly every signal.
    Use "timeout -s KILL".
  * Do not run ./six with stdin from a pipe in a background process group;
    the console driver's read() on /dev/tty produces an endless SIGTTIN
    storm.  Wrap it: script -qec './six' /dev/null


--------------------------------------------------------------------------------
4.  KNOWN ISSUES, IN ROUGH PRIORITY ORDER
--------------------------------------------------------------------------------

Functional
----------
 *  date(1) reports the wrong month: "Wed Aug 19" when the host says
    Sat 19 September.  The day-of-month is right and the time is right, so
    this is a month/weekday conversion bug, most likely in the guest's own
    date program rather than in sys_gettimeofday.  Worth a look; it is the
    only visibly wrong output in the whole session.

 *  Only the toy shell is built on x86.  applications/sh builds just
    interp.o, the while-loop interpreter; the real Bourne shell is built on
    SPARC only.  This matches 2005 and is deliberate, but it means no pipes,
    no redirection, no arguments to commands.

 *  init/getty/login are not used on x86.  init/main.c execs /bin/sh
    directly.  /etc/init is shipped in the image but never run.

 *  The two-trap protocols for mmap() and sigaction() are still in place,
     even though the %esi channel now carries six arguments.  They work; they
     are just ugly, and they are why a single sigaction() shows up twice in
     the trace.

Cosmetic
--------
 *  The console is extremely slow: one write(2) per character, and a full
    re-blit of the screen on every scroll.  A printk near the end of a boot
    can appear dozens of times in a captured log.
 *  "Console: 0 point font, 0 scans"
 *  The "Memory:" line reports nonsense figures (131324k kernel code).
 *  "alloc_area_pte: page already exists" during boot.
 *  Dead code in init/main.c: get_kernel_mask(), uni_lock(), uni_unlock(),
    so_sigset_t.

Not attempted
-------------
 *  SPARC.  Every change is guarded so the SPARC paths are byte-identical to
    2005, but nothing has been compiled for SPARC, let alone run.
 *  Networking.  CONFIG_INET is on and the stack initialises, but there is no
    host-side device behind it.
 *  64-bit.  The tree assumes sizeof(long) == sizeof(void *) == 4 in more
    places than are worth counting.  -m32 is the right answer.

--------------------------------------------------------------------------------
6.  A NOTE ON THE FIVE ORIGINAL BUGS
--------------------------------------------------------------------------------

It is worth saying plainly: none of the five 2003-2005 bugs fixed in this
session were bad code.  Every one of them is a place where a correct Solaris
or SPARC assumption stopped being true.

  * %g6/%g7 exist on SPARC.
  * Solaris' /dev/tty read() semantics differ from Linux's in exactly the way
    that makes "== 0" wrong.
  * The MMX trick works when the operating system does not clear FPU state on
    signal entry.
  * setcontext() reading REG_ESP rather than REG_UESP is a glibc
    implementation detail, and Solaris' is different.
  * The device numbers were right in 2005; they were lost when the image was
    regenerated -- by me.

The author's note on the disk says he left "at a point where the whole thing
compiles on x86, but with various runtime bugs, yet capable of loading
something from the disk and running it".  That was an accurate assessment.
The runtime bugs have now been found.

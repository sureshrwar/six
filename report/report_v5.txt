1.  COMPARING THE 2005 SPARC AND X86 ROOT DISKS
--------------------------------------------------------------------------------

The 2005 SPARC root disk (`v2005-cvs:disk/sparc/root`) is a big-endian rev-0
ext2 image (superblock magic stored as `ef 53` rather than `53 ef`, mount count
477 vs 23 on x86).  Because modern e2fsprogs removed `--swapfs`, we wrote
`port/tools/ext2ls.py` to parse either byte order directly.

What the comparison revealed:
  * SPARC had 47 entries: 23 binaries in `/bin`, `/etc/init`, 8 configuration
    files in `/etc` (`ttytab`, `rc`, `passwd`, `shadow`, `motd`, `hostname`,
    `termcap`, `shelp.txt`), `/usr/lib/fortunes` (24,620 bytes, 434 fortunes),
    and `/usr/adm/wtmp`.
  * x86 had 16 entries: only 8 binaries in `/bin` (where `/bin/sh` was the toy
    while-loop interpreter `interp.c`), `/etc/init` (unused), and `/etc/x86.txt`.
  * On SPARC, both `/dev/console` and `/dev/tty1` are character device `4,1`
    (minor 1), whereas x86 had `/dev/console` at `4,0`.  Because `/etc/ttytab`
    spawns `getty` on `console`, `/etc/init` opens `/dev/console` for fds 0, 1,
    and 2.

All 9 configuration and data files from the SPARC image were extracted into
`port/image/rootfs/` and wired into `port/image/manifest.txt`.

2.  WHAT IT TOOK TO REACH FULL SPARC PARITY
--------------------------------------------------------------------------------

2.1  Building the real Bourne shell on x86 (`applications/sh`)
     `applications/sh/{Makefile,var.c,gmatch.c,do.c,glob.c,word.c,here.c}`

     The 4,485-line Minix Bourne shell (`sh.c` + 12 companion files) had 9
     compile errors under modern GCC, all caused by K&R functions called before
     their definitions (`findeq`, `cclass`, `brkcontin`, `rdexp`, `badid`,
     `generate`, `anyspcl`, `memcopy`, `readhere`).  Added `_PROTOTYPE(...)`
     forward declarations matching `sh.h` and switched `applications/sh/Makefile`
     to build the real shell on both architectures (keeping `interp` as an
     explicit target).

2.2  Implementing i386 `setjmp`/`longjmp` (`library/libc/setjmp_i386.S`)
     `library/libc/setjmp_i386.S`, `library/libc/Makefile`, `Rules.guest`

     The Bourne shell relies on `setjmp`/`longjmp` for its parser, error
     recovery, and loop control (`break`/`continue`), but `library/libc` only
     had a SPARC assembly implementation (`setjmp.s`).  Wrote `setjmp_i386.S`
     implementing `setjmp`, `_setjmp`, `longjmp`, and `_longjmp` (saving and
     restoring the signal mask via `sgetmask`/`ssetmask` to match Minix
     semantics), added a `%.o: %.S` rule to `Rules.guest`, and cleared
     `.DEFAULT_GOAL :=` after `-include $(wildcard .*.o.d)` so dependency files
     do not hijack the default make target.

2.3  Adding the missing `/bin` utilities (`banner`, `cat`, `halt`)
     `applications/Makefile`, `port/image/manifest.txt`

     Added `banner`, `cat`, and `halt` to `SUBDIRS` in `applications/Makefile`
     and added all 23 `/bin` programs (plus `/bin/h`) to `port/image/manifest.txt`.

2.4  Switching the kernel entry point to `/etc/init`
     `init/main.c`

     Removed the `#if (__i386__)` special case that exec'd `/bin/sh` directly.
     Both architectures now `sys_execve("/etc/init", argv_init, envp_init)`.

2.5  Fixing a kernel crash in `ext2_file_write` -> `update_vm_cache`
     `include/linux/pagemap.h`

     When `/bin/login` updated `/etc/utmp` (reading the record left by `init`
     and then writing the `USER_PROCESS` record back), the kernel crashed with
     `SIGSEGV` inside `update_vm_cache()` (`mm/filemap.c:246`).

     Root cause: `update_vm_cache(struct inode *, unsigned long pos, const char *buf, int count)`
     was not declared in any header in `include/`.  In `fs/ext2/file.c:158`,
     `pos` is a 64-bit `loff_t` (`long long`).  Because the call was
     unprototyped, GCC pushed both 32-bit halves of `pos` onto the stack:
     `pos_low` landed in `pos`, `pos_high` (`0x00000000`) landed in `buf`, and
     `bh->b_data + offset` (`0x0b411830`) landed in `count`!  Whenever a file
     already had a page in the page cache (because it had been `read()` before
     being `write()`n), `update_vm_cache` called `memcpy(page, NULL, 188814384)`
     and faulted.

     Adding the prototype `extern void update_vm_cache(struct inode *, unsigned long, const char *, int);`
     to `include/linux/pagemap.h` causes GCC to convert `loff_t pos` to
     `unsigned long` at the call site.

2.6  Fixing the 1-month clock offset (`CMOS_READ(RTC_MONTH)`)
     `include/linux/mc146818rtc.h`

     `date(1)` and `last(1)` both reported `Wed Aug 19` when the host clock was
     `Sat Sep 19`.  In `include/linux/mc146818rtc.h`, SIX emulates the MC146818
     RTC registers by calling the host's `localtime(&tim)` and returning fields
     of `struct tm`.  For register 8 (`RTC_MONTH`), it returned `t->tm_mon`
     (`0..11`), whereas hardware `RTC_MONTH` and `mk_time()` in
     `arch/six/kernel/time.c` expect `1..12`.  Returning `t->tm_mon + 1` makes
     guest time match host time to the second.
